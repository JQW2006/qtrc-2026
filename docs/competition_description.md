# 比赛文档\_赛题说明

## 概览（Overview）

欢迎来到2026量化交易研究大赛！

在真实市场中，预测从来不是一件干净的事情。信号通常很弱，噪声通常很强，而市场状态也在不断变化。一个有效的模型，不仅需要在历史数据中找到规律，还需要判断这些规律在未来是否仍然成立。

本次比赛要求参赛者基于一组匿名化的多标的时序数据，预测每个样本对应的未来风险调整表现。数据包含数百个匿名特征、若干个训练阶段可见的辅助响应变量（responder），以及一个最终用于评分的目标变量 `target`。

参赛者需要构建一个能够按照时间顺序运行的预测模型。在每一个匿名时点，模型只能使用当前及历史已经可见的信息，并为每个匿名标的输出一个连续预测值。

本赛题关注的不只是模型精度，也包括时序验证能力、抗过拟合能力、对非平稳数据的适应能力，以及在受限环境下稳定完成推理的工程能力。

---

## 赛题描述（Description）

现代市场由大量短暂、微弱且相互作用的信号组成。局部趋势、短期反转、波动变化、成交活跃度、流动性状态、路径风险和跨标的联动，都可能在某些状态下影响未来表现。但这些关系并不稳定，也往往难以用简单规则解释。

本次比赛提供一组经过深度匿名化处理的多标的时序数据。每一行代表某个匿名标的在某个匿名时点的市场状态。参赛者将获得：

- 多个匿名标的的连续历史样本；
- 300 余个匿名数值特征；
- 若干个训练阶段可见的 responder；
- 一个最终需要预测的目标变量 `target`；
- 用于评分的样本权重 `weight`。

所有真实标的名称、真实时间信息、原始字段含义、特征构造方式以及目标变量的具体计算方式均匿名化。参赛者不需要，也不应使用任何外部市场信息即可完成比赛。

最终目标 `target` 是一个风险调整表现类目标。它衡量的是当前状态之后某一固定预测窗口内的方向性表现与风险之间的关系。模型输出的正负号代表方向判断，绝对值代表预测强度。

## 评估指标（Evaluation）

比赛使用 **加权零均值决定系数（Weighted Zero\-Mean R²）** 作为评分指标。

设真实目标为 $y$，预测值为 $\hat{y}$，样本权重为 $w$，则评分公式为：

$$
\text{Score}
=
1 -
\frac{
\sum_i w_i (y_i - \hat{y}_i)^2
}{
\sum_i w_i y_i^2
}
$$

其中：

- $y_i$：第 $i$ 个样本的真实 `target`；
- $\hat{y}_i$：参赛者对该样本的预测；
- $w_i$：该样本的权重。

与传统 $R^2$ 不同，本指标以全零预测作为基准。也就是说，如果模型对所有样本都预测 0，则得分为 0。

### 关于权重 `weight`

`weight` 反映不同样本在最终评估中的相对重要性。当前权重主要综合考虑样本对应未来窗口的真实成交活跃度、交易摩擦以及样本本身对整体评估的贡献程度。一般而言，真实成交额更高、摩擦更低的样本会在评分中占据更高权重。

## 代码要求（Code Requirements）

实盘评测阶段将采用顺序推理机制（Time\-Series API）。评测系统会按照匿名时间顺序逐步向参赛者代码提供数据。模型必须在每一步基于当前及历史可见信息返回预测结果。

基本流程如下：

1. 系统提供当前 `time_id` 下的样本特征；
2. 参赛者模型生成对应预测；
3. 系统记录预测；
4. 系统进入下一个 `time_id`；
5. 模型无法访问任何未来特征、未来 responder 或未来目标。

参赛代码需要满足以下要求：

- 能够在官方评测环境中完整运行；
- 不访问外部网络；
- 不使用未授权数据；
- 不读取或推断未来信息；
- 可以加载随策略文件一并提交的预训练模型；
- 在规定时间和内存限制内完成推理；
- 输出格式符合评测 API 要求。

若代码超时、报错或输出非法结果，对应预测将被置为 0；严重情况下，提交可能被判定为无效。

### Time-Series API 接口

私榜阶段的策略提交包必须包含 `main.py`。`main.py` 需要定义 `Model` 类：

```Python
class Model:
    def __init__(self):
        ...

    def predict(self, test):
        ...
```

评测系统会在开始推理前导入 `main.py` 并初始化一次 `model = Model()`。随后系统按严格递增的 `time_id` 循环调用：

```Python
prediction = model.predict(test)
```

其中 `test` 为当前单个 `time_id` 下所有匿名标的的特征表，字段只包含：

```Plain
row_id,time_id,asset_id,feature_*
```

`test` 不包含 `weight`、`responder_*`、`target`、真实时间戳或真实 symbol。每次调用只包含一个 `time_id`，行顺序与官方发布数据一致。参赛者可以在 `Model` 实例内部保存历史状态，因此可以使用当前及历史已经可见的 feature；但不得读取未来测试数据、未来 responder、未来 target、未公开标签或任何未授权数据。

`predict()` 应返回长度等于 `len(test)` 的一维数值结果，顺序与输入 `test` 的行顺序一致。官方 runner 会按照输入行的 `row_id` 生成最终提交文件：

```Plain
row_id,target
```

若 `predict()` 抛出异常、超时、返回长度不一致、返回无法转换为有限浮点数的结果，当前 `time_id` 对应预测默认置为 `0.0`，并记录运行信息。若 `main.py` 无法导入、`Model` 无法初始化，或出现严重资源违规，提交可能被判定为无效；本地测试工具可按全零预测继续生成诊断结果。

本地 Time-Series API runner 会生成两类输出：

- `--output` 指定的提交文件，仅包含 `row_id,target` 两列；
- 标准输出中的 JSON 运行报告，包含 `status`、`rows`、`messages` 和 `timing`。

其中 `timing` 用于本地检查策略推理耗时，包含初始化耗时、预测总耗时、实际调用次数、超时次数、单步最大/平均耗时、总耗时以及是否因超时触发后续全零预测等诊断字段。

### 关于数据的不当使用 \(Data Misuse\)

由于比赛数据来自于真实市场数据，虽已进行充分匿名化，在公榜阶段仍存在通过各种手段进行数据泄露 \(Data Leakage\) 检测、数据渗透 \(Data Exploitation\) 甚至数据入侵 \(Data Hacking\) 从而扰乱公榜秩序的可能。

对未来信息的使用亦可能严重影响公榜秩序，包括但不限于利用未来信息进行数据分析、数据处理、数据建模等。

由于比赛的最终评估建立在实盘数据上，任何数据的不当使用对于最终评分均无任何帮助，只会扰乱比赛秩序。

因此，如果检测到公榜成绩异常，主办方有权先行屏蔽异常成绩，并对相关参赛队伍提出代码审查 \(Code Review\) 要求。如未能成功配合或通过审查，则相应提交将被无效化。如主办方确认参赛队伍存在恶意扰乱公榜秩序甚至比赛秩序行为，队伍成绩将被移出公榜，并可以根据严重程度进行以下处罚：

- 警告并取消当日公榜提交资格；
- 公开警告并取消 n 日公榜提交资格；
- 取消后续提交资格；
- 取消入围评奖资格；
- 取消比赛资格。

## 计算资源与运行限制（Compute Resources）

最终评测阶段将在官方统一环境中运行参赛者提交的策略代码。参赛者可以使用外部资源进行模型训练，但最终提交必须能够在官方环境中稳定完成推理。

评测环境的具体配置以赛题发布后版本为准，初步说明如下：

| 项目         | 说明                                                  |
| ------------ | ----------------------------------------------------- |
| CPU          | 4 核                                                  |
| 内存         | 12 GB                                                |
| GPU          | 最终评测阶段不提供 GPU                                |
| 外部网络     | 不允许访问                                            |
| 运行方式     | 通过 Time\-Series API 顺序推理                        |
| 模型文件     | 允许加载随策略文件一并提交的预训练模型                |
| 运行时间限制 | 以 Time\-Series API runner 和正式评测环境设置为准     |

参赛代码需要在规定时间和内存限制内完成初始化、模型加载和全部预测。本地 runner 支持按单个 `time_id` 设置推理超时，并会在 JSON 运行报告中输出计时统计；正式评测的具体超时阈值和资源限制以最终发布环境为准。若代码出现超时、报错、内存超限、输出非法值或无法完成推理等情况，对应预测将按默认规则处理，严重情况下提交可能被判定为无效。

由于最终评测采用顺序推理机制，参赛者应避免使用过大的模型、过重的特征工程或高耗时的数据处理流程。官方将提供示例代码或本地测试工具，帮助参赛者在提交前检查策略文件是否能够正常运行。

## 提交文件（Submission File）

### 公榜阶段

在公榜测试阶段，参赛者需要为测试集中的每一行提交一个预测值。提交文件为 `csv` 格式，应包含以下两列：

```Plain
row_id,target
0,0.000000
1,0.012345
2,-0.008765
...
```

字段说明：

- `row_id`：测试样本唯一标识；
- `target`：参赛者对目标变量的预测值。

预测值必须为有限浮点数。缺失值、无穷值或无法解析的数值可能导致评分失败，或被系统按默认规则（填充 0 ）处理。

为保证比赛公平性，避免数据渗透，每个参赛队伍每天原则上最多可以进行 `5` 次成功评分。特殊情况需向主办方提出申请，由主办方评估是否提供更多提交次数。

### 私榜阶段

参赛者需要提交策略文件作为最终交付，策略文件为 `zip` 压缩包格式，包含可直接对接评测系统的 `main.py` 主程序，以及所有相关依赖。

各参赛队伍需要在公榜阶段确保提交的代码在评测系统下运行无误，公开数据中将包含示例提交代码和 Time\-Series API 本地测试工具。提交截止日期过后，各参赛队伍无法修改提交代码。如实盘评估阶段运行有错误，系统自动按默认规则（填充 0）处理。

为保证比赛公平性，每个参赛队伍共可以进行最多 `10` 次策略文件提交，最终采用最新提交版本。特殊申请同上。
