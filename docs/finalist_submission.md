# 赛事公告：入围队伍策略包与策略报告提交

## 关于入围队伍策略包与策略报告提交的说明

本文适用于已入围答辩的队伍。未入围队伍不提交本文所述材料。

私榜分数如何计算、如何划定入围名单，以及私榜与评委分如何合成，以《关于策略最终交付与评估的说明》为准。本文只规定入围之后要交回的策略包和策略报告，以及组委会如何核验策略包与私榜实际运行版本一致。

入围队伍须提交两份材料，打在同一个压缩包里：

| 材料 | 作用 |
|---|---|
| 策略复现包 | 包含已提交的推理策略包，以及能够在公榜期间比赛数据上重新得到其中权重的训练代码 |
| 策略报告 | 完整呈现这套策略，供评委阅读和提问 |

## 2. 总原则

报告里讲述的策略、`train/` 复现出的权重、`inference/` 里用于私榜的推理策略，应当是同一套。

1. **推理包保持原样。** 私榜使用的是策略提交截止时已经提交的推理策略包 `submit/`。`inference/` 是该包的直接复制，不在入围阶段改代码、改配置或改权重。
2. **权重来自训练。** 推理时加载的模型权重，以及其他决定预测值的产物，都要能由 `train/` 在公榜期间的比赛数据上得到。手调系数、特征列表、标准化统计量，与模型文件同等对待。
3. **报告对准实际提交的版本。** 报告可以写没有进入最终推理包的试验，建议明确标成未提交实验，以免和跑榜版本混在一起。
4. **数据范围。** 训练、验证和离线调参只使用第 4 节列出的公榜期间比赛数据，不使用外部行情，也不使用能对上真实标的或真实时间的旁路信息。
5. **组委会有权核验。** 核验内容和未通过时的处理见第 5 节。

## 3. 压缩包内容

ZIP 根目录直接放置以下内容，不要再套一层同名文件夹。

```
{team_id}_final.zip
├── README.md               # 简短索引：三部分分别是什么、从哪里看起
├── inference/              # 已提交推理策略包的直接复制
├── train/                  # 复现 inference 中权重的训练代码与说明
│   ├── README.md
│   └── …
└── report/                 # 策略报告
```

根目录 `README.md` 只做索引：推理包对应哪一版已用于私榜的推理策略、训练说明在哪、报告主文件叫什么。训练步骤写在 `train/README.md`，不写进根 README。

不要放入：

- 比赛数据包本身，或自行准备的行情数据
- 完整 Conda 环境、Python 解释器、`venv/`、`conda/`
- `__pycache__/`、`.ipynb_checkpoints/`、`.git/`
- 密钥、Token、内网地址

`inference/` 里原有的相对路径保持不动，不要为了入围提交改写成另一套目录习惯。

### 3.1 推理策略包

`inference/` 直接复制已经提交、并用于私榜评测的那一版推理策略包，包括当时包内的源码、配置、模型权重和其他运行所需文件。原则上原样复制，不做其他更改。

可以去掉的只有与执行无关的缓存，例如 `__pycache__/`、`.ipynb_checkpoints/` 和编辑器临时文件。若原包里混有明确不参与导入、不参与读权重、不参与 predict 的大文件，可以不放入 ZIP，并在根目录 `README.md` 里列出相对路径和省略原因。

除此之外，不要为了整理代码而重构、重命名或重排文件，不要更换权重，不要把几次历史提交合成一个新包，也不要补上原包里没有的后处理。

### 3.2 训练代码

`train/` 用于得到 `inference/` 中的权重文件。这里的权重包括模型参数，也包括推理时会读入、并且会影响预测的其他产物，例如：

- 标准化或分位数等统计量
- 特征列顺序、特征列表
- 集成成员及其混合系数
- 校准参数、阈值、查找表

`train/README.md` 写清下面几项，便于组委会按同一路径重跑：

1. 使用了哪些发布包、各自用于训练、验证还是调参。没有用到的包写明未使用。
2. 公开包如何被调用。写明每个发布包的根目录从哪个参数或配置传入，代码读了其中哪些目录和文件，以及这些文件里用了哪些字段。同时使用两份发布包时，写明如何对齐，例如按 `row_id` 把标签回补包接到主公开包的测试行上。对应的读取代码位置一并标出。
3. 每一步的命令、工作目录、入口脚本和配置文件。数据根目录通过配置或命令行传入，方便组委会挂到自己的路径上。
4. 随机种子。数据打乱、参数初始化、Dropout、各个集成成员，凡是有随机性的地方都要固定，并写进配置。
5. 每一个产物写到哪里，以及它对应 `inference/` 中的哪一个相对路径。
6. 预期运行时间和大致磁盘占用，便于安排核验。
7. Python 依赖及版本，放在 `train/requirements.txt`。这份环境可以与推理包不同。

手工设定的系数也放进配置，不要只留在实验笔记里。在说明里写清它是在哪一段公榜数据上选定的。

可以附带已经算好的中间表，但要同时提供从发布包原始文件生成该表的脚本。重跑时不要再下载数据或依赖。

## 4. 训练数据与推理结果容差

### 4.1 可以使用的数据

训练、验证和离线调参只能使用公榜期间发布的比赛数据：

| 发布包 | 内容 |
|---|---|
| `public_release_20260630` | 主公开包，含训练数据与公榜测试特征 |
| `public_release_20260823` | 标签回补包，与主公开包的测试行按 `row_id` 对齐，并补上 `weight`、`responder_*`、`target` |

标签回补包可以作为扩展训练集或验证集。它对应的是原公榜测试窗口。超参、手调系数和模型选择所依据的样本，都应落在这两份发布包内。

### 4.2 怎样算一致

组委会不对照权重文件本身。用官方副本上的上述发布包，按 `train/README.md` 重跑训练，把得到的权重放回同一套 `inference/` 代码，只替换权重、不改代码，再比较两套权重各自推出的预测。对照使用组委会指定的一段公榜连续时间样本，不由队伍在看到结果之后另行指定。预测落入下面的容差，即视为训练复现了私榜所用的推理策略。记原权重的预测为 $\hat{y}$、训练权重的预测为 $\hat{y}'$。

相对误差只用逐点 MAPE，不设幅度门槛，也不使用绝对误差。记参考序列为 $a_i$、复现序列为 $b_i$，

$$\operatorname{MAPE}(a, b) = \operatorname{mean}_{i:\, a_i \neq 0}\left(\left|\frac{b_i - a_i}{a_i}\right|\right).$$

$a_i = 0$ 的位置不进入平均；这些位置要求 $b_i = 0$。若参考序列全部为 $0$，则复现序列也必须全部为 $0$。

预测容差：

- 相关：$\operatorname{corr}(\hat{y}, \hat{y}') \ge 0.99$
- MAPE：$\operatorname{MAPE}(\hat{y}, \hat{y}') \le 0.001$

相关用来确认两边给出的是同一套信号，MAPE 用来确认没有被整体放大或缩小。整体放大或缩小会直接反映为 MAPE，与预测本身的幅度无关。阈值用来容纳固定种子之外仍然存在的数值误差，不是允许另交一套相近模型。

在通常情况下，若相关校验满足，则不再进行 MAPE 判定。特殊情况相关校验失效时，例如 $\hat{y}$ 或 $\hat{y}'$ 为常数序列，Pearson 相关没有定义，此时按 MAPE 判定（仅作为辅助校验，会进行绝对值阈值截断）。

## 5. 核验与处罚

组委会有权核验每一份入围提交，也可以抽查其中的步骤。队伍应配合。说明和补充材料只用于解释已经提交的包，不能替换压缩包，也不能更换 `inference/`。应组委会要求另行回复的说明，不视为第 1 节所说的第二次提交。

核验可以包括：

1. 将 `inference/` 与实际用于私榜评测的推理策略包对照，确认除缓存和已声明省略的无关文件外，其余文件保持原样。
2. 阅读 `train/` 的说明、代码和配置，确认数据入口落在第 4.1 节的发布包内，产物路径与 `inference/` 中的文件对应得上。
3. 按提交的命令重跑训练，或重跑其中一段能够独立完成的步骤，例如单个种子、单个时间块，或某一份中间表的生成。
4. 把训练得到的权重放回同一套推理代码，按第 4.2 节只比较推理得到的预测，不比较权重文件。

一致性校验未通过时，组委会可要求队伍配合说明，并给予一次补救机会。补救用于解释差异或修正训练复现，不能借此替换已经提交的压缩包或 `inference/`。队伍未配合说明，或补救后仍不能与第 4.2 节的要求相符的，组委会可酌情采取以下一种或几种处理：

- 答辩成绩酌情扣分
- 答辩成绩记 0 分
- 对替换已提交推理策略、训练使用了第 4.1 节以外的数据、或伪造训练路径等严重情形，可以取消入围资格

情节以核验记录和队伍提供的说明为准。

## 6. 策略报告

### 6.1 形式

- 报告放在 `report/`。格式、语言和篇幅不限，评委不借助未提交的链接就能打开即可。
- 包内若有多份文件，建议在根目录 `README.md` 中指明主文件。

### 6.2 建议板块

建议按下面三个板块组织。板块不作强制，队伍可以用自己的结构。每块只列出最有助于评委看清的内容。

#### 策略思路

评委读完后应能复述这套策略。建议写清：

- 预测依据哪些信息，模型做什么；训练目标与加权零均值 $R^2$ 的关系，样本权重是否参与训练
- 每个时点如何把当前输入变成预测。若训练用了 `responder_*` 或 `target`，推理路径如何不依赖这些当时不可见的量
- 若按标的保留历史状态：状态里有什么、何时更新
- 若有多个模型或后处理：它们如何合成最终输出

#### 创新点

建议写清已提交策略相对常见做法多出来的部分。常见做法包括赛会公开示例（线性窗口、LightGBM 等），以及直接对匿名特征做回归或梯度提升。最好展示：

- 创新点落在哪一层：特征或状态、监督信号、损失、样本加权、验证方式、集成或在线更新
- 它针对什么：弱信号、强噪声、非平稳、跨标的差异，或推理时看不到 responder 与 target 的处理
- 若有对照实验：对照的是去掉该创新点之后的方案；写明时间切分和增益。公榜成绩、标签回补后的本地复算和训练期分数分开写
- 做过但没有进入推理包的想法：单独标成未提交实验

#### 鲁棒性

建议说明这套策略在训练窗口之外为什么仍有机会成立。最好展示：

- 验证期相对训练期的表现差异
- 波动、流动性或截面结构变化时策略如何反应；没有自适应机制就写没有
- 换种子、去掉一部分特征或改动主要超参时，指标如何变化
- 信号不可靠，或私榜运行中出现过超时、报错、预测被置 $0$ 时，输出或实际发生了什么，影响哪些样本；描述与 `inference/` 中的代码一致
- 设计时是否考虑过训练期之后的分布变化；没有专门设计就写没有，有则写当时的做法和证据
